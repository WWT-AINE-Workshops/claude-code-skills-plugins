# Lab 4: Package it as a plugin

**SDLC phase:** Secure & Release · **Stage:** AI-Integrated · **Time:** 27 minutes

## Why this matters

Skills in `.claude/skills/` serve one repository. A team that wants the same skills in every repo packages them as a plugin. The plugin has a version and one place to update it, and the team lists it in a marketplace. There are several ways to install a plugin, and each one records it in a different place: your claude.ai account, a folder in the repo, or `.claude/settings.json`. Which one you pick decides whether a teammate who clones the repo gets the plugin.

Here you turn your three skills into the `bookings-toolkit` plugin, list it in a local marketplace called `roombook`, install it from the desktop app, and compare what the other install routes write.

## Steps

### Step 1: Write the plugin manifest

**Do this.** Create `plugins/bookings-toolkit/.claude-plugin/plugin.json` in your editor and write it yourself. It needs:

- `name`: `bookings-toolkit`. It becomes the prefix on every skill in the plugin.
- `description`: one sentence a teammate reads before installing.
- `version`: start at `0.1.0`.
- `author`: an object with a `name`, such as your team's name.

A skeleton, if it helps:

```text
{
  "name": "bookings-toolkit",
  "version": "0.1.0",
  "description": "<what the plugin gives a teammate>",
  "author": { "name": "<your team>" }
}
```

**What you should see.** One file, `plugin.json`, alone inside `plugins/bookings-toolkit/.claude-plugin/`. Nothing else goes in that folder.

**Why.** The manifest names the plugin, and the name is what people type before the colon when they run its skills.

### Step 2: Move the three skills into the plugin

**Do this.** Move the three root skills into the plugin's `skills/` folder with git, so the history follows them. First make the folder.

```bash
mkdir -p plugins/bookings-toolkit/skills
```

What this does: it creates the empty `skills/` folder inside the plugin. It changes nothing else.

Then move the skills.

```bash
git mv .claude/skills/writing-tests .claude/skills/reviewing-code .claude/skills/writing-release-notes plugins/bookings-toolkit/skills/
```

What this does: it moves the three skill folders, with their reference file and script, and stages the move. It leaves `apps/api/.claude/skills/api-conventions/` where it is.

Leave the nested `api-conventions` skill in `apps/api/.claude/skills/`. It describes this repo's API, not a reusable tool, and it loads only when Claude works in `apps/api`. In a plugin it would ship to every repo that installs the toolkit.

**What you should see.** `git status` lists five renames, from `.claude/skills/...` to `plugins/bookings-toolkit/skills/...`, and the untracked `plugins/bookings-toolkit/.claude-plugin/` folder from step 1. The skills sit directly under `plugins/bookings-toolkit/skills/`, not inside `.claude-plugin/`.

**Why.** Moving, not copying, avoids having both `/reviewing-code` and `/bookings-toolkit:reviewing-code` loaded at once.

### Step 3: Write the marketplace file

**Do this.** Create `.claude-plugin/marketplace.json` at the repo root (a new `.claude-plugin/` folder next to `package.json`). It needs:

- `name`: `roombook`. This is what people type after `@` when they install.
- `description`: one sentence about the marketplace, such as what the team keeps in it.
- `owner`: an object with a `name`.
- `plugins`: a list with one entry for your plugin, with `name` `bookings-toolkit`, a `description`, and `source` set to `./plugins/bookings-toolkit`. The source must start with `./`, and it is read from the repo root, not from `.claude-plugin/`.

A skeleton, if it helps:

```text
{
  "name": "roombook",
  "description": "<one sentence about the marketplace>",
  "owner": { "name": "<your team>" },
  "plugins": [
    {
      "name": "bookings-toolkit",
      "source": "./plugins/bookings-toolkit",
      "description": "<one sentence>"
    }
  ]
}
```

**Optional: check both files with the CLI.** Open the Code tab's integrated terminal: click **Terminal** in the session's title bar, or press ``Ctrl+` ``. It opens in the session's folder, the repo root. Run these two there.

```bash
claude plugin validate --strict .
```

What this does: it checks `.claude-plugin/marketplace.json`. It changes nothing.

```bash
claude plugin validate --strict ./plugins/bookings-toolkit
```

What this does: it checks `plugin.json` and the front matter of each skill in the plugin. It changes nothing.

If the terminal says `claude: command not found`, run the same commands through npx. If npx asks to install the package first, answer yes. The npx form downloads Claude Code the first time, which can take a few minutes. On a slow network, skip the optional CLI steps.

```bash
npx @anthropic-ai/claude-code plugin validate --strict .
```

What this does: the same as the first validate command above. It changes nothing.

```bash
npx @anthropic-ai/claude-code plugin validate --strict ./plugins/bookings-toolkit
```

What this does: the same as the second validate command above. It changes nothing.

**What you should see.** Two manifests: `.claude-plugin/marketplace.json` at the root, and `plugins/bookings-toolkit/.claude-plugin/plugin.json` in the plugin. If you validated, each run ends with "Validation passed". It may also print advice for the public plugin directory, such as a missing LICENSE or icon; that advice does not change the result.

**Why.** The marketplace is the catalog: teammates add it once, then install any plugin it lists by name.

### Step 4: Install the plugin from the desktop app

**Do this.** Package the plugin folder as a `.zip`, with `.claude-plugin/` and `skills/` at the top of the archive, not inside a `bookings-toolkit/` folder.

```bash
(cd plugins/bookings-toolkit && zip -qr ../../bookings-toolkit.zip .)
```

What this does: it writes `bookings-toolkit.zip` at the repo root from the contents of the plugin folder. It changes nothing in the plugin. Don't commit the `.zip`.

If the terminal says `zip: command not found`, skip the upload and use route B1 in step 5. It needs no zip and no CLI.

Then upload it from the desktop app.

1. Click **Customize** in the sidebar, then the **Plugins** tab.
2. Click **+ Add**, then **Upload plugin**, and choose `bookings-toolkit.zip`.
3. Start a new session in the Code tab on the participant repo folder, and type `/` in the prompt box.

Know what this does before you click. **Customize** is tied to your claude.ai account, not to this repo. The upload goes to your account, so no teammate gets it from your commit. Claude Code names a plugin that comes from your claude.ai account `bookings-toolkit@synced`. You remove it at the end of the lab.

**What you should see.** **Customize**, on its **Plugins** tab under **Yours**, lists `bookings-toolkit`. If the new Code tab session's `/` list shows `bookings-toolkit:reviewing-code`, `bookings-toolkit:writing-tests` and `bookings-toolkit:writing-release-notes`, the upload worked.

If the three skills do not appear, or your account does not let you upload plugins, use route B1 in step 5. It needs no zip and no CLI. Before you switch, you can type `/reload-plugins` into the prompt box and look once more.

**Why.** An upload is the quickest way to carry a plugin with you, and it shows that "installed" can mean your account, not your repo.

### Step 5: Other ways to install

**Do this.** Read the table. You don't need to run these now; the stretch goals ask you to try one. Use one route at a time. If you run one while the uploaded copy is on, the other route's copy wins and the synced one is not loaded.

| Route                                      | When a team uses it                                                                                            | What it changes                                                             |
| ------------------------------------------ | -------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------- |
| B1: copy the plugin into `.claude/skills/` | The plugin belongs to one repo, and everyone who clones and trusts the repo should get it, with no marketplace | A folder in the repo; loads as `bookings-toolkit@skills-dir`                |
| B2: write `.claude/settings.json` by hand  | You commit settings that declare a marketplace from a git source and turn the plugin on                        | `.claude/settings.json`, written by you                                     |
| C and D: add the marketplace, then install | A teammate's one-time install after they clone, or a setup script                                              | Your machine's plugin records, and `.claude/settings.json` at project scope |

**Route B1.** Copy the plugin folder, with its `.claude-plugin/plugin.json`, into the repo's skills directory.

```bash
cp -R plugins/bookings-toolkit .claude/skills/bookings-toolkit
```

What this does: it copies the plugin into `.claude/skills/bookings-toolkit/`. It changes no settings.

It loads only after you trust the folder, and only when the session starts on the repo root. A `.claude/plugins/` folder is not scanned, so don't put it there.

Claude Code looks for plugins when a session starts. If you accept the trust dialog in a session that is already open, that session looked before you trusted the folder, so the plugin is not there yet. Type `/reload-plugins` in the prompt box, or start a new session. Then type `/` in the prompt box and look for the three `bookings-toolkit:` skills.

**Route B2.** Get your checkout's full path.

```bash
pwd
```

What this does: it prints the full path of the folder you are in. It changes nothing.

The file looks like this, with that path in place of `/path/to/your/copy`. Write the full path: a relative `"."` is not picked up.

```text
{
  "extraKnownMarketplaces": {
    "roombook": {
      "source": { "source": "directory", "path": "/path/to/your/copy" }
    }
  },
  "enabledPlugins": {
    "bookings-toolkit@roombook": true
  }
}
```

Because the marketplace entry's `source` is a relative path (`./plugins/bookings-toolkit`), the plugin needs no install record: it loads from the marketplace itself, once Claude Code knows the marketplace.

**Routes C and D in the desktop app.** In **Customize**, on the **Plugins** tab, click **+ Add**, then **Add marketplace**, and give it this repo's folder. Then, under **In this project**, click **Open folder…**, choose the repo folder, and install `bookings-toolkit` for it. No terminal is needed.

**Routes C and D with the CLI (optional).** In the integrated terminal at the repo root, add the marketplace. In a CLI session (`claude` in a terminal), `/plugin marketplace add ./` does the same; the `/plugin` commands don't run in the Code tab's prompt box.

```bash
claude plugin marketplace add ./ --scope project
```

What this does: it registers the `roombook` marketplace on your machine and declares it in `.claude/settings.json`. It changes no other file.

Then install the plugin for this project.

```bash
claude plugin install bookings-toolkit@roombook --scope project
```

What this does: it installs the plugin on your machine and turns it on in `.claude/settings.json`. It changes no other file.

If `claude` is not found, use these two instead.

```bash
npx @anthropic-ai/claude-code plugin marketplace add ./ --scope project
```

What this does: the same as the marketplace add command above.

```bash
npx @anthropic-ai/claude-code plugin install bookings-toolkit@roombook --scope project
```

What this does: the same as the install command above.

**What you should see.** Nothing changes unless you ran a route. You can say which route records the plugin in your account (A), in a repo folder (B1) or in `.claude/settings.json` (B2, C and D).

**Why.** Knowing where each route records the plugin tells you what a teammate gets from your commit.

### Step 6: Read what the routes write to .claude/settings.json

**Do this.** Route A writes nothing to the repo, so if you only uploaded, you have no `.claude/settings.json`; read the shape below. If you ran routes C and D, open the file in your editor. This is what the CLI writes, with your checkout's full path where `/path/to/your/copy` stands. The order of the two keys can differ.

```text
{
  "extraKnownMarketplaces": {            <- marketplaces this project expects
    "roombook": {                        <- the name after @ in bookings-toolkit@roombook
      "source": {
        "source": "directory",           <- a folder on disk, not a git repo
        "path": "/path/to/your/copy"     <- the full path on YOUR machine
      }
    }
  },
  "enabledPlugins": {                    <- plugins switched on for this project
    "bookings-toolkit@roombook": true    <- plugin@marketplace: on
  }
}
```

What each key means:

- `extraKnownMarketplaces` lists the marketplaces this project expects to exist. Route C writes it here, and not in your user settings, because you chose project scope. Route B2 is the same keys written by hand.
- `roombook` is the marketplace's name from `marketplace.json`.
- `source` says where to fetch the marketplace. `directory` means a folder on disk, and `path` is that folder's full path, written out by the CLI even though you typed `./`.
- `enabledPlugins` says which plugins are on for everyone in this repo. The key is `plugin@marketplace`; `true` means on. Route D writes it.

The `path` is the problem for a team. It points at a folder on your machine. On a teammate's machine it points nowhere, or at the wrong place. If they run route C again, it changes to their path.

For a team, you declare the marketplace from a git source (a GitHub `owner/repo`) instead. A git source means the same on every machine.

A teammate who clones the repo then trusts the folder when Claude Code asks, adds the marketplace and installs the plugin. Plugins and marketplaces from a repo load only after that trust, because committed files can change what Claude Code does.

**What you should see.** You can point to the line that only works on your machine (`path`) and say what a teammate still has to do.

**Why.** Everyone who pulls the repo gets a committed settings file, so check that it means the same thing on every machine.

### Step 7: Run a plugin skill in a new session

**Do this.** Start a new session in the Code tab on the participant repo folder. Then paste this into the prompt box and press Enter:

```prompt

```

Stop once Claude has started its review: when it runs the context script or opens the checklist, the skill has loaded. You don't need the full report: the review changes no code, so you can go on to step 8 while it runs.

**What you should see.** Claude runs the context script from the plugin, which prints the file's line count, its recent commits and `apps/api/test/cancellations.test.ts`, then turns to the checklist. Plain `/reviewing-code` no longer exists.

If the skill is missing, type `/reload-plugins` into the prompt box and try again. If it is still missing, see "If it goes wrong".

In the CLI: run `claude` in the repo folder for the new session.

**Why.** The prefix shows the skill comes from the plugin, so it can sit beside another plugin's skill of the same name.

### Step 8: Commit the plugin, and name what a teammate still has to do

**Do this.** Stage the plugin and the marketplace file only.

```bash
git add plugins .claude-plugin
```

What this does: it stages the new plugin folder and the marketplace file, next to the moves from step 2. It leaves the `.zip` and `.claude/settings.json` unstaged.

Don't commit `.claude/settings.json` from this lab: it holds the full path of your checkout, which is wrong on every other machine. A team commits a settings file with a git source instead.

Commit.

```bash
git commit -m "feat: package the team skills as the bookings-toolkit plugin"
```

What this does: it commits the staged changes on branch `lab-4`. It changes no files.

Then write one line in your notes: what a teammate who clones this commit still has to do before `/bookings-toolkit:reviewing-code` works for them.

**What you should see.** `git status` shows nothing staged. At most three things are untracked: `bookings-toolkit.zip` if you made it, `.claude/settings.json` if you ran route B2, C or D, and `.claude/skills/bookings-toolkit/` if you ran route B1. Your line names a route for the teammate, for example: trust the folder, add the marketplace and install at project scope.

**Why.** Saying the teammate's steps out loud is how you find the gaps before they do.

## If it goes wrong

- **The reset stops with "You have uncommitted or untracked changes".** Commit or stash your lab 3 work, or throw it away with the command below.

  ```bash
  ./scripts/reset-lab.sh 4 --force
  ```

  What this does: it discards your uncommitted changes and untracked files, then resets as in "Before you start".

- **Validate says the source must start with "./".** The plugin's `source` in `marketplace.json` reads `plugins/bookings-toolkit`. Make it `./plugins/bookings-toolkit`.
- **The upload is refused, or the three skills don't appear after it.** Check the `.zip`: `.claude-plugin/plugin.json` must be at the top of the archive. Rebuild it with the command in step 4, from the repo root. If it still fails, or your organization does not allow uploads, use route B1.
- **`zip: command not found`.** Your terminal has no `zip`. Skip the upload and use route B1 in step 5.
- **Route B1 does not load.** Trust the folder when Claude Code asks, and start the session on the repo root, not on a subfolder. Then type `/reload-plugins`, or start a new session: a session that was open when you trusted the folder looked for plugins before the trust.
- **"Marketplace file not found".** You ran route C from a subfolder, such as `apps/api`, so `./` pointed there. Run it from the repo root, where `.claude-plugin/marketplace.json` is.
- **The install says the plugin is not found in marketplace `roombook`.** The marketplace is not added on this machine yet. Run the marketplace add command first.
- **Both `/reviewing-code` and `/bookings-toolkit:reviewing-code` show.** The old skills are still in `.claude/skills/`. You copied them instead of moving them. Delete the copies under `.claude/skills/` (keep `apps/api/.claude/skills/`).
- **Nothing works.** Without the CLI, use route B1, or follow the rest of the lab on the facilitator's screen. With the CLI, and signed in to it, you can load the plugin for one session without installing it. Run this in the integrated terminal, then try the skill in that session. Point it at the plugin folder, not the repo root: at the repo root it loads nothing.

  ```bash
  claude --plugin-dir ./plugins/bookings-toolkit
  ```

  What this does: it starts a Claude Code session in the terminal with the plugin loaded. It writes nothing to settings.

- **You're on Windows with WSL.** Plugins do not load in the Code tab's WSL sessions. Follow the facilitator's screen, or use the Windows-side copy from pre-work Step 8 in a local Windows session, with route B1.

**The clean-up, route by route.** In the desktop app, **+**, then **Plugins**, then **Manage plugins** shows what is installed, and lets you disable or uninstall it without the CLI.

Route A: click **Customize** in the sidebar and remove `bookings-toolkit` from its plugins. Then delete the archive.

```bash
rm bookings-toolkit.zip
```

What this does: it deletes the `.zip` from the repo root. It changes nothing else.

```bash
rm -r .claude/skills/bookings-toolkit
```

What this does: it deletes the plugin copy under `.claude/skills/`. It leaves `plugins/bookings-toolkit/` alone.

```bash
claude plugin uninstall bookings-toolkit@roombook --scope project
```

```bash
claude plugin marketplace remove roombook
```

What this does: it removes the `roombook` marketplace from your machine and empties its `extraKnownMarketplaces` entry. Removing it alone also uninstalls any plugin you installed from it.

If `claude` is not found, use these two instead.

```bash

```

What this does: the same as the uninstall command above.

```bash
npx @anthropic-ai/claude-code plugin marketplace remove roombook
```

What this does: the same as the marketplace remove command above.

Then delete the settings file, which now holds two empty entries and was never committed.

```bash
rm .claude/settings.json
```

What this does: it deletes `.claude/settings.json`. It changes nothing else.

An installed copy of the plugin can stay in Claude Code's plugin cache under `~/.claude/plugins/cache/` after clean-up. It no longer loads, and it does no harm.
