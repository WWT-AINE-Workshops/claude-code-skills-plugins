# Lab 3: Release notes, then tune the trigger

**SDLC phase:** Secure & Release · **Stage:** AI-Assisted · **Time:** 26 minutes

## Why this matters

Release notes mix two kinds of work. Grouping the commits since the last release is exact work, and the repo already has a tool for it. Turning those groups into plain words for API users is judgement work, which Claude does well. A good skill hands the exact part to the script and keeps the prose for Claude.

A skill also has to load at the right time. Here you also test when Claude loads yours: three prompts that should load it, three that should not, each in a fresh session. Then you fix the description until the table is right.

## Before you start

Run the reset script from the repo root.

```bash
./scripts/reset-lab.sh 3
```

What this does: it switches you to branch `lab-3` at the start of this lab and resets the local database to the seed (4 members, 5 rooms, 20 bookings). The `writing-tests`, `reviewing-code` and `api-conventions` skills are now the reference versions at this tag, not the ones you wrote in labs 1 and 2; your lab 2 work stays on branch `lab-2`. You don't need the dev server in this lab.

Work in the Code tab of the Claude desktop app, in a local session on the participant repo folder.

## Steps

### Step 1: Write the release-notes skill

**Do this.** Create `.claude/skills/writing-release-notes/SKILL.md` in your editor and write it in your own words. It needs these parts:

- Front matter with `name: writing-release-notes` and a `description`. Write the description in the third person, and say what the skill does and when to use it, key use first. Use the words people say when they want release notes.
- A first step that runs the release tool and uses its groups. Tell Claude to run the tool, not to read the git log itself for this step. The tool lists the commits since the last `chore(release):` commit in four groups: breaking, features, fixes and other.
- A check: compare the groups with the git log since that release commit, and stop and say so if a commit is missing.
- How to write the notes: for API users, not the team. Breaking changes first, each with what a client must change, then new features, then fixes. Leave out chore, docs, test and workshop commits. One plain line per change, no commit hashes.
- What to do with the draft: show it, and edit `CHANGELOG.md` only when asked.

This command prints the groups as JSON. Put it in your skill's first step:

```bash
npm run changelog --silent -- --json
```

What this does: it reads the git history and prints the grouped commits. It changes nothing.

A skeleton, if it helps:

```text
---
name: writing-release-notes
description: <what it does>. Use when <the requests that should load it>.
---

# Writing release notes

1. <Run the release tool. Say what its groups are.>
2. <Check the groups against the git log.>
3. <How to write the notes, and what to leave out.>
4. <Show the draft. When to touch CHANGELOG.md.>
```

Then start a new session in the Code tab on the participant repo folder, and type `/` in the prompt box.

**What you should see.** `writing-release-notes` is in the list, next to `writing-tests` and `reviewing-code`. If it is missing, check the path and that the opening `---` is the very first line of the file.

**Why.** The script makes the grouping the same every time, so Claude spends its effort only on the prose.

### Step 2: Ask for release notes and compare with the log

**Do this.** Run your skill directly. Paste this into the prompt box and press Enter:

```prompt
/writing-release-notes
```

When Claude shows the draft, look at the history yourself in a terminal (the Code tab's Terminal, or any terminal in the repo folder).

```bash
git log --oneline -7
```

What this does: it lists the last seven commits, newest first, ending with `chore(release): 0.2.0`. It changes nothing.

Then look at the tool's own output.

```bash
npm run changelog --silent
```

What this does: it prints the grouped commits as Markdown. It changes nothing.

**What you should see.** The log has six commits after `chore(release): 0.2.0`. Find each one in the tool's output, and note any commit that is in no group. Then read the draft as a client would: does it tell them everything they must change? If your skill has the check from step 1, Claude may point out a gap itself.

**Why.** The skill repeats whatever the tool gets wrong. Comparing the tool's output with the git log shows any gap.

### Step 3: Fix the release tool

**Do this.** Ask Claude to fix the parser. Paste this into the prompt box and press Enter:

```prompt
The release tool in packages/release-tools drops breaking changes: a subject with the ! marker, like feat(api)!: ..., is skipped, and a BREAKING CHANGE: footer in the body is ignored. Fix src/changelog.ts so both put the commit in the breaking group. Add tests for both cases to test/changelog.test.ts, then run the package's tests.
```

When Claude is done, run the package's tests yourself.

```bash
npm test -w @roombook/release-tools
```

What this does: it runs the release tool's tests. It changes nothing.

Then print the groups again.

```bash
npm run changelog --silent
```

What this does: it prints the grouped commits as Markdown. It changes nothing.

Finally, run your skill again. Paste this into the prompt box in the same session and press Enter:

```prompt
/writing-release-notes
```

**What you should see.** The tests pass, and there are more of them than the 16 the package had at the start. The tool's output now starts with a Breaking changes section that lists "require X-Member-Id on bookings". Your skill's new draft puts that change first and says that clients must send the `X-Member-Id` header.

**Why.** The fix belongs in the tool, so every run of the skill gets it, not only this one.

### Step 4: Fill in the trigger table

**Do this.** Run each of the six prompts below in its own new session in the Code tab, on the participant repo folder. A fresh session matters: an earlier prompt in the same session can change what Claude does.

After each prompt, watch the transcript. When Claude loads your skill, you see it use `writing-release-notes`, and Claude starts with your skill's first step, the release tool. You don't need to let a prompt run to the end once you can tell. If you can't tell, paste this into the same session and press Enter:

```prompt
Did you load a skill to answer that? If so, which one?
```

In the CLI: run `claude` in the repo folder for each new session.

Short of time? Run two of each: S1, S2, N1 and N2, and score out of 4.

These three should load the skill.

S1. In a new session, paste this into the prompt box and press Enter:

```prompt
Draft the release notes for the next Roombook release.
```

S2. In a new session, paste this into the prompt box and press Enter:

```prompt
What's new for API users since the last release?
```

S3. In a new session, paste this into the prompt box and press Enter:

```prompt
Our clients want to know what changed since 0.2.0. Summarize it for them.
```

These three should not load it.

N1. In a new session, paste this into the prompt box and press Enter:

```prompt
What changed in the last commit?
```

N2. In a new session, paste this into the prompt box and press Enter:

```prompt
How does packages/release-tools decide which group a commit goes in?
```

N3. In a new session, paste this into the prompt box and press Enter:

```prompt
Suggest a commit message for my change to packages/release-tools/src/changelog.ts.
```

Keep score in this table. Copy it into a note, or onto paper, and tick the last column when what happened matches what should happen.

| Prompt | Should load | Loaded? | Right? |
| ------ | ----------- | ------- | ------ |
| S1     | yes         |         | [ ]    |
| S2     | yes         |         | [ ]    |
| S3     | yes         |         | [ ]    |
| N1     | no          |         | [ ]    |
| N2     | no          |         | [ ]    |
| N3     | no          |         | [ ]    |

**What you should see.** A score out of 6. A first description often gets one or two rows wrong:

- A "should load" prompt does not load it. The description lacks the words people use.
- A "should not" prompt loads it. The description is too broad, for example it matches any mention of commits or the changelog.

Another skill, such as `reviewing-code`, loading for a "should not" prompt is fine: the question is only whether `writing-release-notes` loaded.

**Why.** Seeing a skill load once proves Claude found it, not that it loads only when it should.

### Step 5: Fix the description, then decide who starts it

**Do this.** Edit the `description` in your `SKILL.md`, then re-run only the rows that were wrong, each in a new session. Repeat until the table is right. Two common fixes:

- A miss: add the words from the missed prompt, such as "what's new", "for clients" or "since the last release".
- A false load: make the description more specific. Say it is for notes for users about a release, not for a single commit or for explaining the tool.

Then decide whether this skill should set `disable-model-invocation: true` in its front matter. Know the trade-off before you choose. With it set, Claude never loads the skill on its own, and the description is no longer in Claude's context at all. Your three "should load" prompts then stop loading the skill, and you run it only by typing `/writing-release-notes`. Without it, Claude loads the skill whenever a request matches the description.

Write one line under your table: your choice, and why. If you set it, change the "Should load" column to "no" for every row and re-run one "should load" prompt to see it no longer loads.

**What you should see.** Every row in your table is ticked, and you have one line that says whether the skill sets `disable-model-invocation` and why.

**Why.** The description decides when the skill loads; `disable-model-invocation` decides whether Claude may start it at all.

### Step 6: Commit

**Do this.** Stage the skill and the tool fix.

```bash
git add .claude/skills/writing-release-notes packages/release-tools
```

What this does: it stages your skill and the release tool changes. It changes no files.

Commit them.

```bash
git commit -m "fix(release-tools): list breaking changes in release notes"
```

What this does: it commits the staged changes on branch `lab-3`. It changes no files.

**What you should see.** `git status` shows a clean tree. If you run `npm run changelog --silent` now, your own commit shows under Fixes, because it is a `fix` commit since the last release.

**Why.** Once the skill is committed, everyone who pulls the repo gets it.

## You're done when

`npm run changelog --silent` starts with a Breaking changes section that lists "require X-Member-Id on bookings", and your trigger table has every row ticked. Post ✓ and your score in the chat, for example "✓ 6/6, Claude can load it" or "✓ 6/6, on request only". If you are stuck, post SOS and the step number.

## If it goes wrong

- **The reset stops with "You have uncommitted or untracked changes".** Commit or stash your lab 2 work, or throw it away with the command below.

  ```bash
  ./scripts/reset-lab.sh 3 --force
  ```

  What this does: it discards your uncommitted changes and untracked files, then resets as in "Before you start".

- **`writing-release-notes` is not in the `/` list.** The file must be `.claude/skills/writing-release-notes/SKILL.md`, with `SKILL.md` in capitals, and the opening `---` must be the first line. Start a new session after you fix it.
- **The skill runs with `/writing-release-notes` but never loads on its own.** Read the front matter line by line. A value that contains `: ` (a colon and a space) must be in quotes, or the front matter does not parse and Claude sees no description. Put the whole description in double quotes if you are not sure.

- **The draft in step 2 already lists the breaking change.** Claude read the git log itself instead of the tool's groups. That hides the bug. Make step 1 of your skill say to use the tool's groups, not the log. The tool's own output (`npm run changelog --silent`) is the reliable check.
- **The notes list the workshop commits or "add workshop materials".** The tool puts those under Other. Your skill should say to leave out chore, docs, test and workshop commits.
- **The tests fail after the fix.** Ask Claude to run `npm test -w @roombook/release-tools` and fix what fails. A footer only counts when a line in the body starts with `BREAKING CHANGE:`, not when the words appear in the middle of a sentence.
- **Every prompt loads the skill, or none does.** None: the description lacks the words people use, or the front matter does not parse. Every one: the description is too broad. In both cases, re-read the description as if you were Claude choosing between your skill and the others.

## Recap

You built a skill that gives the exact part of release notes to a script and the writing to Claude. You compared the script's output with the git log, and found and fixed a bug. Then you tested when the skill loads, with six prompts in fresh sessions. You tuned the description until the table was right, and chose whether Claude may start the skill on its own.
