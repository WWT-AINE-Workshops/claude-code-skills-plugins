# Lab 2: A code review skill, with a nested skill

**SDLC phase:** Test · **Stage:** AI-Assisted · **Time:** 26 minutes

## Why this matters

A good review follows the same checklist every time, and it starts from the same facts: how big each file is, what changed in it lately, and which tests cover it. If you paste that checklist into every chat, it costs context and drifts. A skill keeps the steps short in `SKILL.md`. The checklist goes in a reference file that loads only when needed. A script gathers the facts and gives the same answer every run.

Some rules belong to one part of the repo only. The Roombook API has its own conventions for errors, members and ownership. A nested skill in `apps/api/.claude/skills/` loads only when Claude works in that folder, so it costs nothing anywhere else. In this lab you build both skills, review the API with them, and prove what the review finds.

## Steps

### Step 1: Write the review skill

**Do this.** Create `.claude/skills/reviewing-code/SKILL.md` in your own words. Keep it short: the steps go here, the detail goes in the checklist file you write next. It needs:

- Front matter with `name: reviewing-code` and a `description`. Write the description in the third person. Say what the skill does and when to use it: reviewing, auditing or checking a file, a route or a change.
- A body of numbered steps that tells Claude to:
  - run the context script on what is under review, and read the files it lists;
  - work through the checklist;
  - check each finding before reporting it, with a test, a `curl` call or a short script, and drop what cannot be shown;
  - report the findings in a table, most severe first;
  - change no code during the review.
- A link to `references/checklist.md`, and the command that runs the script, written with `${CLAUDE_SKILL_DIR}` so it works from any folder.

This skeleton shows the shape. Fill in each part yourself:

```text
---
name: reviewing-code
description: <what it does>. Use when <the requests that should load it>.
---

# Reviewing code

1. Collect the facts: bash "${CLAUDE_SKILL_DIR}/scripts/review-context.sh" <files or commits>
2. Work through [the checklist](references/checklist.md) ...
3. ...
```

Then create `.claude/skills/reviewing-code/references/checklist.md`. Start from this skeleton, and add one or two questions of your own to each section. Write questions that apply to any code, not answers about this repo:

```text
# Review checklist

## Authorization
- Who may make this request, and where does the code check it?

## Input validation
- Is every path parameter, query parameter and body field checked before use?

## Data access
- How does each SQL statement get its values?

## Errors
- Does each error go through the app's shared error type, with the right status code?

## Tests
- Is there a test for the success path and for each refusal?
```

**What you should see.** Two files under `.claude/skills/reviewing-code/`. The front matter starts on line 1 with `---`, `SKILL.md` is about 10 to 15 lines, and the checklist has five sections of two or three questions each.

**Why.** Claude reads `SKILL.md` when the skill loads and opens the checklist only when it reaches that step, so the core file stays small.

### Step 2: Add the context script

**Do this.** Let Claude write the exact part. Paste this into the prompt box and press Enter:

```prompt
Create .claude/skills/reviewing-code/scripts/review-context.sh. It takes one or more file paths or git commits. For a commit, it uses the files that commit touched. For each file it prints the file name, its line count, its last three commits, and the test files (*.test.ts) that are named after it or mention its base name. With no arguments it prints a usage line and exits 2. Use bash with set -euo pipefail. Do not change any other file.
```

When it is done, run the script on the files you review in step 4:

```bash
bash .claude/skills/reviewing-code/scripts/review-context.sh apps/api/src/routes/cancellations.ts apps/api/src/repo.ts
```

What this does: prints facts about the two files. It changes nothing.

**What you should see.** One block per file: `cancellations.ts` has 18 lines, one recent commit (`feat(api): serve rooms, bookings and availability over HTTP`) and `apps/api/test/cancellations.test.ts` as its test. `repo.ts` has 93 lines. No test file is named after it, so whether a test shows under it depends on how your script matches names. Run it with no arguments and it prints a usage line.

**Why.** Counting lines and reading `git log` must give the same answer every time, so a script does it and Claude only runs it.

### Step 3: Write the nested API skill

**Do this.** If your facilitator says to skip this step, go on to the next one.

Create `apps/api/.claude/skills/api-conventions/SKILL.md` in your own words. Read `apps/api/src/errors.ts` and `apps/api/src/members.ts` first. It needs:

- Front matter with `name: api-conventions` and a `description` that says it holds the Roombook API's rules, for use when writing, changing or reviewing code under `apps/api`.
- Three short rules:
  - errors are thrown as `HttpError` from `src/errors.ts`;
  - the acting member comes from the `X-Member-Id` header through `actingMember()`, and a missing or unknown member is 401;
  - one rule of your own for routes that change or delete data, from what you read in the code.

**What you should see.** A `SKILL.md` under `apps/api/.claude/skills/api-conventions/` with front matter on line 1 and three to five lines of rules.

**Why.** A skill in a subfolder's `.claude/skills/` loads only when Claude reads or edits a file in that folder, so its rules cost nothing when you work elsewhere.

### Step 4: Review the API in a new session

**Do this.** Start a new session in the Code tab on the participant repo folder, so it picks up both skills from a clean start.

Type `/` in the prompt box (or use **+**, then **Slash commands**) and look for your skills. Then press Esc and paste this into the prompt box, without naming the skill:

```prompt
Review the API routes in apps/api/src/routes/ and the data access in apps/api/src/repo.ts. Report what you find, most severe first.
```

When the review is done, type `/` again and look for `api-conventions`. If you are not sure, paste this into the prompt box:

```prompt
Which skills did you load during this review?
```

In the CLI: run `claude` again in the repo folder for the new session, and type `/skills` to list the loaded skills.

**What you should see.** Before the review, `/reviewing-code` is in the list and `api-conventions` is not. During the review, Claude runs `review-context.sh` and opens `references/checklist.md`: that shows `reviewing-code` loaded. After Claude has opened a file in `apps/api`, `api-conventions` shows in the list too (if you skipped step 3, it does not, and your facilitator shows it instead).

The report is a table, most severe first. Look for a finding you could prove with one request to the running API. The wording differs from run to run. Check each finding against the code before you accept it.

**Why.** The review skill loaded without being named, so its description matches the request. The nested skill stayed out of the way until Claude worked in its folder.

### Step 5: Reproduce the bug

**Do this.** In a terminal at the repo root, reset the database first. A check Claude ran during the review may have changed a booking.

```bash
npm run setup
```

What this does: typechecks the code and resets the local database to the seed. It changes no source files.

Then start the API and leave it running.

```bash
npm run dev
```

What this does: starts the Roombook API on port 3001 and restarts it when a source file changes. It changes no files.

In a second terminal, list the bookings for room 1 on 2 November.

```bash
curl -s 'http://localhost:3001/api/bookings?roomId=1&date=2026-11-02'
```

What this does: reads the bookings. It changes nothing.

Now cancel booking 1, which belongs to member 1 (Ava Patel), as member 2 (Ben Okafor).

```bash
curl -si -X DELETE http://localhost:3001/api/bookings/1 -H 'X-Member-Id: 2'
```

What this does: sends the cancel request as member 2. While the bug is there, it deletes booking 1 from your local database.

**What you should see.** `npm run setup` ends with `4 members, 5 rooms, 20 bookings`. The list shows two bookings, ids 1 ("Platform stand-up", member 1) and 5. The cancel prints `HTTP/1.1 204 No Content`. Run the list again and only booking 5 is left. Member 2 cancelled a booking that was not theirs.

**Why.** A finding you reproduce is a finding you can prove fixed.

### Step 6: Fix it with a test, then re-run

**Do this.** Paste this into the prompt box and press Enter:

```prompt
Fix the ownership bug in DELETE /api/bookings/:id: only the member who made a booking may cancel it. Any other known member gets 403 with the error "Only the member who made a booking can cancel it", and the booking stays. Write the failing test first in apps/api/test/cancellations.test.ts, show it fail, then fix the route and run npm test.
```

The reproduction deleted booking 1, so put it back before you check the fix. Stop the dev server (press Ctrl+C in its terminal), then reset the database.

```bash
npm run setup
```

What this does: typechecks the code and resets the local database to the seed, so booking 1 is back. It changes no source files.

Start the server again.

```bash
npm run dev
```

What this does: starts the API with your fix on port 3001.

In the second terminal, send the same cancel request as member 2.

```bash
curl -si -X DELETE http://localhost:3001/api/bookings/1 -H 'X-Member-Id: 2'
```

What this does: tries to cancel booking 1 as member 2. With the fix, nothing is deleted.

**What you should see.** Claude shows the new test failing with 204 where it expects 403, changes `apps/api/src/routes/cancellations.ts`, and `npm test` passes. `npm run setup` ends with `4 members, 5 rooms, 20 bookings`. The cancel request now prints a 403 status line and a JSON body with your error message. List the bookings again and booking 1 is still there.

**Why.** A test that failed before the fix and passes after it keeps the bug from coming back.

### Step 7: Commit

**Do this.** Stop the dev server (press Ctrl+C in its terminal). Stage the two skills, the fix and the test.

```bash
git add .claude apps/api
```

What this does: stages your new skills and the changed files under `apps/api`. It changes no files.

Then commit them.

```bash
git commit -m "fix(api): only the member who made a booking can cancel it"
```

What this does: commits the staged changes on branch `lab-2`.

**What you should see.** `git status` shows a clean tree, and `git log -1` shows your commit.

**Why.** Skills in `.claude/skills/` are part of the repo, so your team gets them with the next pull.

## You're done when

The cancel request as member 2 prints a 403 status line and booking 1 is still in the list. Post ✓ in the chat. If you are stuck, post SOS and the step number.

## If it goes wrong

- **`api-conventions` does not show after the review (step 4).** Paste this into the prompt box, then ask for the review again:

  ```prompt
  Open apps/api/src/routes/bookings.ts and tell me what it does.
  ```

  If it still does not show, note it and carry on: `reviewing-code` finds the bug on its own. Check the path is exactly `apps/api/.claude/skills/api-conventions/SKILL.md`.

- **`reviewing-code` does not load (step 4).** Check the front matter starts on line 1 with `---` and the description names reviewing. Then run it by name: type `/reviewing-code` at the start of the prompt, followed by the same request.
- **The review does not mention cancellations.** Ask Claude to go through the authorization section of your checklist for `apps/api/src/routes/cancellations.ts` only.
- **The review flags something you are not sure about.** Open the code it names and see how the value reaches it. Ask Claude to prove the finding with a `curl` call or a test. If it cannot, drop it.
- **The cancel prints 404 `Booking 1 not found`.** Booking 1 is already gone: your reproduction, or a check Claude ran during the review, deleted it. Stop the server, run `npm run setup`, start the server again and retry.
- **`npm run dev` fails with `EADDRINUSE`.** Another server holds port 3001, maybe from lab 1 or one Claude started. Stop it in its terminal, or ask Claude to stop the server it started.
- **The script does not run.** Run it with `bash` in front, as in step 2, and check the path. The script needs to be inside a git repository.
