# Lab 1: Your first skill: writing tests

**SDLC phase:** Test · **Stage:** AI-Assisted · **Time:** 26 minutes

## Why this matters

You probably ask Claude for tests the same way every time: use Vitest, follow the repo's helpers, cover the edge cases. A skill writes that down once. It is a `SKILL.md` file with a short description and a body of instructions. Claude reads the description on every turn and loads the body only when a request matches it.

Roombook is a small meeting-room booking API. The booking rules in `apps/api/src/booking-rules.ts` decide whether two bookings clash, and nothing tests them directly. In this lab you write a `writing-tests` skill with a checklist of boundary cases, ask for tests without naming the skill, and let the checklist find a real bug.

## Before you start

Open a terminal in the participant repo folder and run the reset script. In the Code tab, click **Terminal** in the session's title bar, or press ``Ctrl+` ``, to open one in the session's folder.

```bash
./scripts/reset-lab.sh 1
```

What this does: switches you to a fresh branch `lab-1` at the start of this lab, installs packages if they changed, and resets the local database to the seed data (4 members, 5 rooms, 20 bookings). It stops and changes nothing if you have uncommitted work.

Work in the Claude desktop app's **Code tab**, in a local session on the participant repo folder. The repo has no `.claude/` folder yet, so no project skills exist.

## Steps

### Step 1: Take a baseline

**Do this.** In your Code tab session, paste this prompt into the prompt box and press Enter:

```prompt
What skills are available in this session? List them by name and say where each one comes from.
```

In the CLI, or if your app shows it: type `/skills` to see the same list.

**What you should see.** A list that may include built-in or personal skills, but nothing from this repo and nothing called `writing-tests`.

**Why.** You need a "before" to compare with, so you can tell later that your skill is the one that loaded.

### Step 2: Write the skill

**Do this.** Create the file `.claude/skills/writing-tests/SKILL.md` in the repo, in your editor or by asking Claude to create it with text you give it. Write it in your own words. It needs these parts:

- **Front matter** between two `---` lines, starting on the very first line of the file:
  - `name: writing-tests`, which becomes the command `/writing-tests`.
  - `description`: one or two sentences, in the third person, that say what the skill does and when to use it. Use the words a person would type, such as "write tests", "add tests" or "cover this file".
- **A body** of numbered steps that tells Claude to:
  - read the code under test first and list what it exports;
  - use Vitest, put tests in `apps/api/test/<module>.test.ts`, import pure functions from `../src/<module>`, and use `makeTestApp()` from `./helpers` for routes;
  - write table-driven cases with `it.each`, one row per case, each with a name that says what it proves;
  - always cover the boundaries: equal values, adjacent values (one range ends exactly where the next starts), empty input, and one step past each limit;
  - run the tests, and report a failing case as a possible bug instead of changing the code or the test to make it pass.

The file has this shape:

```text
---
name: writing-tests
description: <what it does>. Use when <the requests that should load it>.
---

# Writing tests

1. Read the code under test ...
2. Put the tests in ...
3. Write table-driven cases ...
4. Always cover the boundaries:
   - ...
5. Run the tests. If a case fails ...
```

**What you should see.** One new file at `.claude/skills/writing-tests/SKILL.md`, about 15 to 25 lines long. Nothing else changes.

**Why.** The description decides when the skill loads, and the checklist in the body decides what the tests cover.

### Step 3: Ask for tests without naming the skill

**Do this.** Start a new local session in the Code tab on the same folder. The `.claude/skills/` folder did not exist when your first session started, so that session does not see the new skill yet. In the new session, paste this prompt into the prompt box and press Enter:

```prompt
Add unit tests for apps/api/src/booking-rules.ts. It has no tests yet.
```

Approve the file write and the test run when Claude asks.

In the CLI: quit and run `claude` again in the repo folder, or type `/reload-skills` in the same session.

**What you should see.** The session shows that Claude used the `writing-tests` skill before it wrote any code. Then a new file `apps/api/test/booking-rules.test.ts` appears, with `it.each` tables and rows for each kind of boundary in your checklist. Claude runs the tests and reports the results. For any failing case, check that Claude calls it a possible bug and leaves the code alone. If you are not sure the skill loaded, ask Claude which skill it used.

**Why.** A skill is only useful if Claude picks it from the request alone, without you naming it.

### Step 4: Run the tests yourself

**Do this.** In a terminal in the repo folder, run the API's tests.

```bash
npm test -w @roombook/api
```

What this does: runs the Vitest suite for the API package only. It changes no files.

**What you should see.** Every existing test file passes, and `booking-rules.test.ts` has one or more failing rows. Read their names: which boundary from your checklist do they share? Your row names and counts depend on what Claude wrote.

**Why.** The checklist asked for boundary cases the existing tests never tried, so a failing row there is a lead on a bug in the code.

### Step 5: Fix the bug

**Do this.** In the same Code tab session, paste this prompt into the prompt box and press Enter:

```prompt
The back-to-back cases fail. Two bookings where one ends exactly when the next starts should not overlap. Fix overlaps() in booking-rules.ts, keep the tests as they are, then run the whole test suite.
```

Then run the whole suite yourself from the repo root.

```bash
npm test
```

What this does: runs the tests for every package in the repo. It changes no files.

**What you should see.** Claude changes the two comparisons in `overlaps()` so that touching ends no longer count, and leaves the test file alone. Every test file in every package passes, including `booking-rules.test.ts`.

**Why.** The new tests now guard the rule, and the rest of the suite shows the fix broke nothing else.

### Step 6: Commit

**Do this.** Stage the skill, the new test file and the fix.

```bash
git add .claude/skills/writing-tests apps/api
```

What this does: stages your skill and your changes under `apps/api`. It leaves everything else unstaged.

Then commit them.

```bash
git commit -m "test(api): cover booking rules and fix back-to-back overlap"
```

What this does: records the staged files as one commit on branch `lab-1`. It does not push.

**What you should see.** Git reports one commit with three files: `SKILL.md`, `booking-rules.test.ts` and `booking-rules.ts`. A later `git status` shows a clean tree.

**Why.** The skill lives in the repo, so anyone who clones it gets the same test-writing habits.

## You're done when

`npm test` passes, `apps/api/test/booking-rules.test.ts` exists, and `git log -1` shows your commit. Post ✓ in the chat with the name of the bug your skill found. If you are stuck, post SOS and the step number.

## If it goes wrong

- **The skill does not load in step 3.** Check the front matter starts on line 1 with `---` and that the file is at `.claude/skills/writing-tests/SKILL.md`. Then run it by name: type `/writing-tests` at the start of the prompt, followed by the same request. You can also type `/` or use **+** then **Slash commands** to see it in the list. You tune the description in lab 3.
- **`/writing-tests` is not in the list.** The session started before the folder existed. Start another new session.
- **No test fails in step 4.** The tests skipped the adjacent case. Ask Claude to add rows where one booking ends exactly when the next starts, in both orders, then run the tests again.
- **Claude changed the test, not the code.** Undo that change and ask again, saying the test is right and `overlaps()` is wrong. Make sure your skill's last step says to report a failure, not fix it.
- **`reset-lab.sh` refuses to run.** You have uncommitted changes. Commit them, or run it again with `--force` to throw them away.

## Stretch goals

- Add `argument-hint` to the front matter, such as `[file to test]`, then run the skill on a file of your choice. Paste this into the prompt box in a new session and press Enter:

  ```prompt
  /writing-tests apps/api/src/members.ts
  ```

- Move the Vitest details into `.claude/skills/writing-tests/references/vitest-patterns.md`, and add one line to `SKILL.md` that says when to read it. Keep `SKILL.md` to the steps and the checklist.
- See the fix in the running API. Start the server in a terminal:

  ```bash
  npm run dev
  ```

  What this does: starts the API on port 3001 and keeps it running. Stop it later with Ctrl+C.

  Then, in a second terminal, book room 1 from 10:00 to 11:00 on 2 November as member 2, right after the 09:00 stand-up:

  ```bash
  curl -s -i -X POST http://localhost:3001/api/bookings -H 'Content-Type: application/json' -H 'X-Member-Id: 2' -d '{"roomId":1,"title":"Mobile one-to-one","startsAt":"2026-11-02T10:00:00.000Z","endsAt":"2026-11-02T11:00:00.000Z"}'
  ```

  What this does: asks the API to create one booking, which changes the local database when it succeeds. With your fix it returns `201 Created`. Run it a second time and it returns `409 Conflict`, because your own booking now holds that slot. Run `npm run setup` to put the seed data back.

## Recap

You wrote a skill with a name, a description that says what and when, and a boundary checklist. Claude loaded it from a plain request, and the checklist found a back-to-back booking bug that the existing tests missed.
